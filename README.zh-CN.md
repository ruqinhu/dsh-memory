# @ruqinhu/dsh-memory

[English](README.md) | 中文

给 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的长期记忆：
两份文档、一个硬性的字符预算，以及一个模型能顺着跳回去的索引。

DSH 本身不带持久记忆包，于是每个新会话都从「忘记上个会话学到的规则」开始。这个插件用
`§` 分隔的条目维护 `MEMORY.md`（长期规则）和 `USER.md`（owner 是谁），把它们作为动态
提示上下文注入；当文档大到无法整份展示时，给模型一条按 id 读回单条的路。

下面按约束逼出设计的顺序展开。第 1 节是决定一切的那个约束；第 2–6 节每节一个机制，每节都
先讲促成它的那次失败，再点名被否决的替代方案；第 7 节是实测；第 8 节是还没解决的问题。
安装、配置与工具速查放在最后 —— 论证落地之后，读者才需要它们。

## 1. 决定一切的约束

记忆不是带滚动条的数据库。它是提示上下文，每次请求都要付费，而它挤占的正是任务要用的窗口。

所以两份文档都有硬性字符上限。会让结果超限的写入被**拒绝**，而不是截断：

| 文档 | 默认上限 | 为什么要有上限 |
| --- | --- | --- |
| `MEMORY.md` | 2,200 字符 | 长期规则，一条一条长起来 |
| `USER.md` | 1,375 字符 | owner 的画像与长期偏好 |

截断是记忆文件悄悄出错的典型方式：写入看起来成功了，下一次请求却少了某条约束。拒绝写入
会逼出那份迟早要做的压缩。参照的 Hermes 部署就是反面案例 —— `MEMORY.md` 涨到 3,687
字符（超 68%）、`USER.md` 涨到 2,748（超 100%），而整条链路里没有任何一处察觉。

上限做成配置项而非常量，是因为诚实的做法是：先调高上限、压缩完、再调回来。

### 各部分的位置

```text
  MEMORY.md ─┐
             ├─ 按 § 切分 ─► 条目 ─► id = hash(目标, 正文)
  USER.md ───┘                  │
                                ├─ 合计 ≤ 6,000 字符 ─► 整份内联进提示（上下文顺序 130）
                                └─ 合计 > 6,000 字符 ─► 索引，每条一行：
                                     "- m-3f7a1c2d5e · 止损 2.96/走弱 3.02"
                                          │
                             memory_get(id) ◄─┘   第二跳
                                │
  召回 / 检索 ─► 打分后的条目 ─► 按预算排版（放不下就跳过，绝不截断）
  读取、召回、检索 ─► .entry-index.json ─► 命中次数、首次/最近时间
                                                       │
                                 memory_maintenance ───┘ 冷条目清单，按字符数降序
```

## 2. 注入：装得下就整份，装不下就给索引

把记忆放到模型面前有两种方式，而它们朝相反方向出错。

**2.1 整份内联**在文本还小时严格更优：不花工具往返，规则就在眼前。

**2.2 索引**要花一次调用，但不会挤占工作上下文。

分界线是合计 6,000 字符。低于它整份注入；高于它改为注入索引。没有这个切换，长起来的记忆
会悄悄吃掉它本该支撑的窗口；而一直用索引，则是让所有小规模部署白白付一次往返。

索引放在上下文顺序 130 —— 团队身份（125）之后、harness 源码（200）之前 —— 并且通过
`systemPrompt.context()` 注册，而不是 `agent/pre-step`。上下文接缝本来就是「把持久的
user-role 快照物化为动态上下文」的官方位置，它的 text 提供者在每次装配时重新求值；
`pre-step` 则要在每一步伪造一条 user 消息，等于替 harness 签发它从未发过的消息 id。

## 3. 身份：ID 把索引从「猜」变成「跳」

被截断的首行不是引用。在条目有 ID 之前，索引给每条展示 80 个字符，然后让模型去调
`memory_search` —— 想读一条规则剩下的部分，只能去猜恰好出现在里面的关键词。

现在每个条目都有 ID：`MEMORY.md` 用 `m-` 前缀、`USER.md` 用 `u-`，后面是条目正文哈希的
十位十六进制。索引打印它，`memory_search` 返回它，召回块里的每一行带着它，`memory_get(id)`
按它读回单条全文。

比格式更重要的有两点：

- **ID 是算出来的，不是存进去的。** 每次加载从文档重算，所以已有记忆零迁移、手改过的条目
  自然拿到新 ID，而文档始终是 owner 的 —— 正文里不会多出哈希给压缩过程添乱。
- **规则被改，ID 就换。** 这才是诚实的：被读过的那条规则，已经不是现在存在的这条规则。
  对过期 ID 调 `memory_get`，回答是「请调用 `memory_search`」，而不是在同名下返回另一条规则。

位置编号（`第 7 条`）因此被否决：每次压缩都会重排，模型上一轮写下的所有引用会静默指向
另一条规则。

**3.1 为什么不做向量检索。** 最顺手的现代替代是向量索引：把每条嵌入，按相似度取回。它在这个
部署上有三个过不去的点。它要解决的失败 —— 「规则和问法的措辞不同」—— 并不是这里真正发生的
失败；这里真正发生的是**规则过期**，相似度检索看不出这一点，而第 5 节的用量统计看得出。
向量索引还是第二份真相：一旦某次压缩改写了条目，它就和文档开始漂移。而且它在每次写入和每次
查询上都要付一次嵌入调用，而这个插件的前提恰恰是「记忆应该是便宜的」。关键词二元组加一个能
跳的 ID，在召回率上更差，但在可解释性上远好：当某条规则没被召回来，原因就摆在查询词里。

## 4. 检索：按 owner 真正打的字来切

中文没有词分隔符，所以查询只有被切成能匹配的单元才有用。整段保留 —— 也就是之前的行为 ——
只在查询恰好是条目子串时命中：

```
查询  止损怎么设
条目  止损 2.96/走弱 3.02     → 得分 0，召回静默返回空
```

而「0 分」和「记忆里确实没有相关内容」完全无法区分，这条路径就是这样长期形同虚设的。
现在查询按**二元组**切分（`止损`/`损怎`/`么设`），含 `止损` 的条目就能命中 owner 真正打过
的字。单字仍然不切（`跌` 保留），否则几乎命中每一条，打分就退化成噪声。

召回按字符预算（默认 1,500）、从高分到低分填充，放不下的条目**跳过而非截断**：半条规则读起来
像完整的一条，比没有更糟。

`memory_recall`（默认关闭）返回排版好的块加一行指示 —— `🧠 召回 N 条记忆`。指示行存在的
理由是没有确定性信号时，「模型选择沉默」和「召回坏了」长得一模一样。它按变化报一次，而不是
每回合都报：一行永远不变的字就不再是信息，而是背景板。

自动召回（默认关闭）在每回合第一步跑同一条检索，三条规则都来自踩过坑的部署：

- **琐碎回合不召回** —— 不是查完再丢弃，而是根本不查。`好的` 靠一个字就能命中大半条目，
  查它等于把一条无关规则塞进一个什么都没问的回合。判定用词表而不是长度，因为 `跌停` 和
  `止损` 也只有两个字，却是这位 owner 发得最密的提问。
- **召回失败绝不让回合失败。** 记忆是优化项；连回合一起丢掉，等于用变差的回答换来没有回答。
- **查询只用 owner 自己写的字。** pre-step 的批次里还带着记忆文档、技能目录和时间上下文 ——
  拿那些去召回，等于让记忆和自己比对。

注入块的 `source.kind` 是 `'system-prompt'` 而不是 `'user'`：它是 harness 放进去的上下文，
标成 `user` 等于每次回放会话都在替 owner 说话。

## 5. 压缩需要证据，而不是品味

上限逼着必须删掉点什么。没有证据时，选择默认退化成「我碰巧又读到哪条」—— 一条仍然有效的
规则就这样被删掉，而一条死规则又活了一年。

**5.1 侧车。** 每次召回、检索、显式读取都按条目 ID 在 `.entry-index.json` 记一次命中，同时
记录 `firstSeenAt` 与 `lastHitAt`。文件每次同步都从文档重建：被删的条目随之失去统计，被改的
条目从头开始。自动召回触发的写入做了合并（每分钟最多一次），因为计数器不值得每回合写一次文件。

**5.2 报告。** `memory_maintenance` 列出「没用过的」：超过 45 天没有被命中、按字符数从大到小、
最多十二条 —— 而且年轻于 14 天的条目永不出现，因为昨天刚写的规则只有一天的被用机会，而一份
全是新条目的报告会训练读者忽略它。

证据是**下界，不是判决**。每次请求都被整份内联注入的条目，一直在用却永远不会被计数，所以
冷条目是复核候选，永不自动删除；报告里也这么写，插件里没有任何代码会删条目。

**5.3 一次压缩的完整流程。**

1. `memory_maintenance` —— 备份两份文档、报告用量、列出冷条目。
2. 逐条读冷条目再动手。它可能只是一条「上周才开始有用」的规则。
3. 用 `memory_replace` 合并相关规则，而不是直接删：同一主题的两条规则通常能压成一条，比
   单独任何一条都短。
4. 再跑一次 `memory_maintenance`。用量回到上限内、冷清单变短 —— 这就是可以停的信号。

## 6. 纪律做成技能，而不是注入的协议

「什么时候该写记忆、怎么压缩」是流程，不是数据。每请求注入一遍协议，等于把「写规则的规则」
也塞进上下文 —— 而这恰好是本插件存在的意义所反对的。

profile 带技能注册表（`@deepseek-ai/dsh-skill`）时，插件把 `memory-curation` 注册进去：
该存什么、追加还是替换、怎么用 ID、怎么拿冷条目清单当证据做压缩。目录只花一行，正文只在
真正碰记忆的那些回合按需加载。

注册走的是**延迟子 fiber**（`ctx.inject(['skills'])`），不是 `static inject`：把技能注册表
写成必需依赖，会让没有注册表的 profile 整个插件都加载不起来 —— 用一个技能换掉全部记忆，
是很糟的交易。`enableSkill: false` 则用于「有注册表但不想要这个技能」的部署。

## 7. 实测

- **单测**：118 个、15 个文件；每个决策（上限、ID、索引渲染、二元组打分、召回预算、冷条目
  选择）都是可单测的纯函数，`tsc --noEmit` 在 `strict` 下干净。
- **线上往返**：`memory_search("网关")` 返回 `m-efa7252010`；对该 id 调 `memory_get` 拿回
  完整的 95 字符条目；第二次调用被侧车计入（该条目 `hits: 2`）。
- **技能注册**：让线上 agent 列自己的技能目录，`memory-curation` 在列。
- **线上形态**：参照部署跑 38 条条目、上限调到 3,000 字符，仍低于 6,000 的内联阈值 —— 所以它
  读的是整份内联，ID 只在维护报告和「模型想原样读某一条」时用到。

## 8. 开放问题

- **自动召回默认关闭。** 它要等注入切换到索引之后才有价值；在上限之内整份记忆本就常驻上下文，
  召回只会再注入一份。接缝先定下来，是为了那时不用改结构。
- **`snapshot()` 返回的是活记录，不是副本。** 对维护报告方便，作为命名却有误导；测试就是
  通过它改状态的。
- **冷清单是抽样**（十二条）—— 够指导一次压缩，不是完整清单。
- **规则一改，统计清零。** 这是有意的，但意味着频繁改写会藏掉复核者可能想看的用量历史。
- **没有跨文档去重。** 同一条规则同时出现在 `MEMORY.md` 和 `USER.md` 会被算作两条，没有任何
  东西会合并它们。
- **上限是字符，不是 token。** 对散文两者相关性够用，对中英混排则完全不成立 —— 换语言的部署
  应该重新量一次，而不是信这个数字。
- **没有跨设备同步。** 文档就是 `memoryDir` 下的文件；两台机器共享一份记忆需要一套本插件
  没有的加锁方案。

## 安装

```bash
dsh plugin add @ruqinhu/dsh-memory
```

bundle patch 通过 `package.json` 里的 `dsh.bundle` 自动应用。

## 配置

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `memoryCap` | `2200` | `MEMORY.md` 字符上限 |
| `userCap` | `1375` | `USER.md` 字符上限 |
| `enableInjection` | `true` | 是否作为动态上下文注入 |
| `backupKeep` | `12` | 保留的备份目录数 |
| `memoryDir` | `~/.dsh/memory` | 文档与备份目录 |
| `enableRecall` | `false` | 是否注册 `memory_recall` |
| `enableAutoRecall` | `false` | 是否每回合自动召回一次 |
| `recallBudgetChars` | `1500` | 单次召回注入的字符上限 |
| `staleAfterDays` | `45` | 多久未被使用即算「冷条目」 |
| `staleMinAgeDays` | `14` | 年轻于此天数的条目永不报为未使用 |
| `enableSkill` | `true` | profile 有技能注册表时注册 `memory-curation` 技能 |

## 工具

| 工具 | 用途 |
| --- | --- |
| `memory_read` | 读文档，含用量与条目数 |
| `memory_get` | 按 ID 读单条全文 |
| `memory_search` | 关键词检索，按得分返回（带 ID） |
| `memory_recall` | 检索并排版成可直接使用的上下文块（`enableRecall`） |
| `memory_write` | 整体替换（超上限拒绝） |
| `memory_append` | 追加一条（超上限拒绝） |
| `memory_replace` | 精确替换子串 |
| `memory_maintenance` | 备份、轮转、报告用量与冷条目 |

`memory_replace` 是压缩用的原语：原地改写过期规则，而不是重写整份文档 —— 后者是最容易
丢规则的做法。

## 每周维护

参考部署每周六跑一次压缩。把定时任务指向 `memory_maintenance`，再让 agent 以冷条目清单为
证据，用 `memory_replace` 合并或删除条目，直到用量回到上限内。
