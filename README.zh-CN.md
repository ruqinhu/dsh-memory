# @ruqinhu/dsh-memory

[English](README.md) | 中文

给 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 提供**字符上限可配置**的长期记忆。

DSH 本身没有持久记忆包，会话之间会丢规则。本插件维护两份以 `§` 分隔的文档，并在每次装配时作为动态上下文注入。

## 为什么不用截断

截断是记忆文件悄悄出错的典型方式：写入看起来成功了，下一次请求却少了某条约束。**超上限的写入会被拒绝**，逼出一次真正的压缩。

参照场景：迁移前 Hermes 的 `MEMORY.md` 已涨到 3,687 字符，上限 2,200（超 68%）；`USER.md` 涨到 2,748，上限 1,375（超 100%）。

## 安装

```bash
dsh plugin add @ruqinhu/dsh-memory
```

## 配置

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `memoryCap` | `2200` | `MEMORY.md` 字符上限 |
| `userCap` | `1375` | `USER.md` 字符上限 |
| `enableInjection` | `true` | 是否作为动态上下文注入 |
| `backupKeep` | `12` | 保留的备份目录数 |
| `memoryDir` | `~/.dsh/memory` | 文档与备份目录 |
| `enableRecall` | `false` | 是否注册 `memory_recall` |
| `enableAutoRecall` | `false` | 是否每回合自动召回一次 |
| `recallBudgetChars` | `1500` | 单次召回注入的字符上限 |
| `staleAfterDays` | `45` | 多久未被使用即算「冷条目」 |
| `staleMinAgeDays` | `14` | 年轻于此天数的条目永不报为未使用 |
| `enableSkill` | `true` | profile 有技能注册表时注册 `memory-curation` 技能 |

上限做成配置项，是为了迁移期先把上限调高、压缩完再调回来。

## 注入策略

文档较小时整体注入。合计超过 6,000 字符后改为注入**条目索引**并提示调用 `memory_search`，避免记忆膨胀后静默挤占工作上下文。

## 检索与召回

分词对中文按**二元组**切分（`止损怎么设` → `止损`/`损怎`/`么设`）。这不是细节：整段保留时，查询必须恰好是条目的子串才能命中，于是 `止损怎么设` 对条目 `止损 2.96/走弱 3.02` 得 **0 分**，召回静默返回空 —— 和「记忆里确实没有相关内容」完全无法区分，正是这条路径曾让检索形同虚设。单字仍不切分（`跌` 保留），否则几乎匹配每一条。

`memory_search` 返回带分数与来源的**条目列表**，给模型自己看。

`memory_recall`（默认关闭）返回**已排版好的上下文块**加一行指示（`🧠 召回 N 条记忆`），按分数从高到低填充，直到字符预算耗尽；放不下的条目**跳过而非截断** —— 半条规则读起来像完整的一条，比没有更糟。

为什么召回默认关闭：文档还在 6,000 字符以内时，整份记忆本来就常驻上下文，召回只会**再注入一份**。它要等文档涨过内联预算、注入转为索引之后才有价值。接口先定下来，是为了那时不用改结构。

指示行照搬 Hermes 的 `describe_recall` 理由：没有确定性指示时，「模型选择沉默」和「召回坏了」无法区分。这个部署在投递侧已经吃过一次同样的亏。

### 自动召回

`enableAutoRecall`（默认关闭）在模型没主动要求的情况下跑同一条检索，时机是**每回合的第一步**，注入结果只属于这一回合。三条规则直接来自 Hermes 的 `prefetch`，每一条背后都有一次事故：

- **琐碎回合不召回。** 不是查完再丢弃，而是**根本不查**。`好的` 靠一个字就能命中大半条目，查它不只是白读一次，而是把一条无关规则塞进一个什么都没问的回合里。判定用词表（`好的`/`收到`/`ok`/…）而不是长度 —— `跌停` 和 `止损` 也只有两个字，却是这位 owner 发得最密的提问。
- **召回失败绝不让回合失败。** 记忆是优化项；连回合一起丢掉，等于用一个变差的回答换来没有回答。
- **指示只报一次，不是每回合都报。** 一行永远不变的字就不再是信息而是背景板，然后「召回坏了」和「召回沉默」又长得一模一样。

注入块是 `user` 角色但 `source.kind` 为 `'system-prompt'`，不是 `'user'`。它是 harness 放进去的上下文；标成 `user` 等于每次回放会话都在替 owner 说话。

查询只用 owner 自己写的字。pre-step 的批次里还带着记忆文档本身、技能目录和时间上下文 —— 拿那些去召回等于让记忆和自己比对，命中永远是已经在上下文里的那份文档。

## 条目 ID 与第二跳

每个条目都有稳定 ID：`MEMORY.md` 用 `m-` 前缀，`USER.md` 用 `u-`，后面是十位十六进制，由条目正文派生。

ID 的存在是因为**索引只有能被跳回去才有用**。在此之前，超预算注入把每条渲染成 80 字首行再指向 `memory_search` —— 想读一条首行被截断的规则，只能去猜恰好出现在里面的关键词。ID 把「猜」换成「跳」：`memory_get('m-3f7a1c2d5e')` 直接返回索引刚刚点名的那一条；召回块里的每一行也带自己的 ID。

ID 由内容派生而非按位置编号，这是有意的。位置编号（`第 7 条`）在每次压缩后都会重排，于是模型上一轮写下的所有引用会静默指向另一条规则。内容哈希只在规则本身变化时变化 —— 那正是旧引用应该失效的时刻，也是 `memory_get` 对过期 ID 回一句「请调用 memory_search」而不是返回空的原因。

ID **不写进** `MEMORY.md` / `USER.md`。文档是 owner 的，正文里多一个 ID 就给压缩多一处出错的地方；而且 ID 每次加载时从文档重算，所以已有记忆零迁移，手改过的条目自然拿到新 ID。

## 压缩的证据

`memory_maintenance` 把「哪些条目真被用过」—— 召回、检索、按 ID 读取 —— 记进 `.entry-index.json` 侧车文件，并列出超过 `staleAfterDays` 未被使用的条目，按字符数从大到小排。

上限逼着必须删掉些什么，而没有证据时，选择默认退化成「我碰巧又读到哪条」—— 一条仍然有效的规则就这样被删掉，而一条死规则又活了一年。证据是下界而非判决：每条请求都被整份内联注入的条目，一直在用却永远不会被计数，所以冷条目是**复核候选，永不自动删除**。年轻于 `staleMinAgeDays` 的条目根本不会出现；昨天刚写的规则只有一天的被用机会，而一份全是新条目的报告会训练读者忽略它。

## 记忆纪律技能

profile 带技能注册表（`dsh-skill`）时，插件把 `memory-curation` 注册进去：什么时候该写、怎么避免写重复、怎么压缩。

纪律做成技能而不是注入的协议，因为协议要被看见就必须每次请求都发一遍 —— 而这恰好是本插件存在的意义所反对的。目录只花一行，流程只在真正碰记忆的那些回合按需加载。技能两个方向都是可选的：没有注册表的 profile 直接跳过注册（`enableSkill: false` 也会跳过）。

## 工具

| 工具 | 用途 |
| --- | --- |
| `memory_read` | 读文档，含用量与条目数 |
| `memory_get` | 按 ID 读单条全文 |
| `memory_search` | 关键词检索，按得分返回（带 ID） |
| `memory_recall` | 检索并排版成可直接使用的上下文块（`enableRecall`） |
| `memory_write` | 整体替换（超上限拒绝） |
| `memory_append` | 追加一条（超上限拒绝） |
| `memory_replace` | 精确替换子串 |
| `memory_maintenance` | 备份、轮转、报告用量与冷条目 |

`memory_replace` 是压缩用的原语：原地改写过期规则，而不是重写整份文档。

## 每周维护

参考部署每周六跑一次压缩。把定时任务指向 `memory_maintenance`，再让 agent 以冷条目清单为证据，用 `memory_replace` 合并或删除条目，直到用量回到上限内。
